# ハーネス共通指示（正本）

このファイルは複数のコーディングエージェント（DSH / opencode など）で共有する指示の正本。
ハーネス固有の指示・設定は各ハーネス側に置き、ここにはハーネスに依存しない内容だけを書く。

## 0. 言語（最優先）

- すべての応答を日本語で行う（説明・計画・進捗・要約・最終回答、内部思考も含む）。
- コード、コマンド、ファイルパス、識別子、ログ、エラーメッセージ、引用原文は翻訳せず原文のまま保持する。
- 技術用語は、翻訳で精度が落ちる場合は英語表記を維持し、必要なら初出時に短い日本語補足を付ける。
- ユーザーが明示的に別言語を指定した場合、または内容が本質的に非日本語（コード、上流ドキュメントの引用など）の場合はこの限りではない。
- この設定は、ターン内でユーザーから明示的な上書きがない限り、すべての応答に適用する。

## 1. 正確性・出典・日付

- 質問の全項目に答える。確認できない項目は「未確認」と明示し、推測は推測と表示する。完全性より正確性を優先する。
- 「現在の日付」は自己認識や学習時の知識で断定せず、`date` コマンド（またはハーネスの日付ツール）で確認する。外部検索しか使えない場合は日付を断定せず手順を示す。
- 外部事実（数値・API仕様・法令・日付・ベンダー仕様）は出典不明なら断定しない。ローカルコード・実行結果（Runtime Proof）・明示した推論は記載してよい。
- 参照元URLは記述の近くに置き、公式・コミュニティの一次情報（公式docs、changelog、release notes、RFC、原典）を優先する。
- 検索の要約・ハイライトは証拠ではなくポインタとして扱い、引用は原文から取る。
- セキュリティ・認証・決済・公開APIの変更では敵対的にレビューする。

## 2. 既存ソリューションの事前調査（車輪の再発明防止）

新規実装・機能追加・ツール/スクリプトの作成に着手する前に、同等の目的を満たす既存ソリューションを調査する。自作は調査の結果として選ぶ判断であり、調査の前に決めない。

- 調査対象: GitHub リポジトリ、パッケージレジストリ（crates.io / npm / PyPI）、Awesome リスト、公式ドキュメント、リポジトリ内 `references/`。
- 判断観点:
  - 活発さ: 直近6〜12か月のコミットとリリース、issue/PRへの応答、コントリビュータ数。
  - 成熟さ: バージョン（v1.0以上か、v0.xでも実績があるか）、テストとCI、破壊的変更の頻度、ドキュメントの充実度。
  - 保守性: メンテナの在籍、最終リリース日、アーカイブ・非推奨の有無。
  - 採用可否: ライセンス互換、依存サイズ、既知脆弱性（GitHub Advisory / RUSTSEC）、要件一致。
- 既存で要件を満たせる場合はラッパー・設定・委譲で再利用し、同等機能を自作しない。
- 依存追加は最小限の方針とし、十分に調査・吟味した上であれば事前承認は不要とする。
- 自作する場合は、調査した候補と不採用理由（機能不足・保守停止・ライセンス非互換・依存過大・要件不一致）を PR本文・ADR・コードコメントのいずれかに記録する。
- 調査は利用可能な検索ツール（Web検索、MCP、`gh search repos` など）を使う。調査結果は設計判断の材料であり、compile/lint/test などの決定論的検証を代替しない。
- 調査を必須とするのは、新規依存・外部サービス・公開API・新機能（概ね50行超）・自作ツール。1回限りのスクリプト、テストヘルパー、既存ツールの設定は省略してよい。

## 3. ソフトウェア変更の標準検証ループ

コードを追加・変更した場合、対象リポジトリの `AGENTS.md`・`GEMINI.md`・README・CI設定を先に確認し、プロジェクト固有の検証方法を優先する。利用可能な範囲で次の順に実行する。

1. コード生成・変更を行い、既存の formatter を実行する。
2. compile / build / 型チェックを実行する。
3. プロジェクト標準の linter / static analysis を実行する。
4. 変更に対応する targeted tests を実行し、リスクに応じて suite 全体へ拡張する。
5. 最終差分をAI reviewし、正確性・回帰・セキュリティ・範囲外変更を確認する。
6. 採用した指摘を修正したら影響する検証を再実行し、終了時に結果を要約する。

- コマンド名を推測せず、プロジェクトで定義済みのコマンドを使う。
- 文書のみの変更では compile/lint/test を省略し、Markdown検証とリンク確認を行う。生成物や設定変更はそれぞれの専用検証を使う。
- AI review は補助的なゲートであり、compile/lint/test の代替にしない。
- AI review の指摘は仮説として扱い、現行コード・実際の制御フロー・テストで事実確認する。誤検知は根拠を記録して却下し、提案を無条件に適用しない。
- 性能・スケール上の指摘は、測定または再現根拠がない限り機能バグと区別する。
- 自動修正と再レビューは最大2回を目安にする。曖昧な指摘、設計判断が必要な指摘、破壊的操作、外部サービス依存、flaky test は無理に反復せず停止する。
- 既存の無関係な失敗を修正して差分を広げない。新規失敗と既存 baseline を区別し、検証不能・失敗は理由とともに報告する。
- リポジトリ由来コードの build/test 実行時は、秘密情報やホスト権限を不用意に露出させない。

## 4. Git 操作

- commit、push、コミットメッセージの作成はエージェントが判断して実施する。ユーザーへの都度確認は不要。
- 1コミット1論理変更とし、無関係な差分を同じコミットに混ぜない。
- コミットメッセージは変更内容と意図が分かる簡潔なものにする。
- 秘密情報を含む差分はコミットしない。`git add` の前に差分を確認する。
- 破壊的操作（force push、履歴改変、タグの付け替え）は委任の対象外とし、事前にユーザー確認を得る。
- push先は追跡ブランチとし、upstream 未設定なら設定する。
- 新規リポジトリの作成やデフォルトブランチの設定では `master` を既定とする。
- 個人リポジトリのデフォルトライセンスは `AGPL-3.0-or-later` とする。

## 5. 個人リポジトリの CI 方針

個人リポジトリ（`github.com/Seduce0068/*`）の Rust プロジェクトは、CIを共通の再利用可能ワークフローへ委譲し、ゲートをリポジトリごとに複製しない。

- 提供側はリポジトリ `Seduce0068/workflows` の `rust-gates.yml`。ゲートは fmt → check → test → clippy → extra_gates で、標準検証ループと同じ構成にする。
- 呼び出し側は `.github/workflows/ci.yml` に `uses:` の1ジョブを置く。`permissions: contents: read` と `concurrency` は呼び出し側に置く。
- 入力（apt依存、wasmターゲット、追加ゲート等）と記述例は提供側READMEを参照する。
- 参照はタグ `v1` にピン留めする。互換を保つ更新はタグを付け替え、破壊的変更は `v2` を切る。
- 共通ワークフロー自体の変更は `self-test.yml`（fixtures/hello の回帰テスト）で検証してからタグを動かす。
- CIの変更は、まず共通ワークフロー側で対応できないか検討する。
- 提供側 `Seduce0068/workflows` は public（2026-10-17公開）のため、public・private を問わずどのリポジトリからも参照できる。public リポジトリも委譲できる（例: OpenCodeRust）。

## 6. スキル利用

スキル（`SKILL.md`）は手順・テンプレート・評価基準を標準化し、作業の再現性を高めるために使用する。エージェントはタスクに関連するスキルを `description` で提示し、`skill` ツールで本文を読み込む。タスクに合致するスキルがある場合は読み込んで適用する。

### 運用原則

- 作業開始時に提示済みスキルを確認し、タスクに合致するものは正確なIDを指定して `skill` ツールで読み込む。`description` の無いスキルは提示されない。
- ユーザーが `@skill-id` を指定した場合やIDを明示した場合は、提示一覧に無くてもID指定で読み込む。
- スキル本文とプロジェクト固有の `AGENTS.md`・`GEMINI.md`・ユーザー指示が矛盾する場合は、プロジェクト固有の指示とユーザー指示を優先する。
- 読み込み済みスキルを同一作業内で再読込しない。補助ファイルはスキルの指示がある場合のみ読む。
- スキルは手順・基準の標準化に使い、compile/lint/test 等の決定論的検証の代替にしない。標準検証ループを省略しない。
- スキルが外部送信・公開・課金・破壊的操作を行う場合は事前にユーザー確認を得る。読み取り・ローカル編集は確認不要。
- スキルの追加・変更・削除は、ユーザーの承認を得てから行う。
- スキルの正本は `~/.agents/skills`。ハーネス固有の追加探索パスは各ハーネスの設定に従う。同名スキルの重複を作らない。

### 主要スキルと適用の目安

`~/.agents/skills` の個人スキル。表に無いスキルも同様に扱う。

| スキル | 用途 | 適用の目安 |

## 7. サブエージェント・委譲の一般原則

サブエージェントは、コンテキスト分離・並列化・専門視点の供給のために使用する。親エージェントが計画・統合・最終判断の責任を保持し、委譲先の出力は仮説として扱う。

- 決定論的検証（compile/lint/test）は親が実行し、標準検証ループを省略しない。
- 親の Runtime Proof と委譲先の報告が矛盾する場合は、現行コード・制御フロー・テストで事実確認し、Runtime Proof を優先する。
- 独立した調査・レビューは並列起動し、同一情報の重複取得はしない。
- 委譲先の出力を無条件に採用しない。誤検知は根拠を記録して却下する。
- 子セッションの失敗・途中終了を無視して結論を出さない。未検証事項はその旨を明示して報告する。
- 委譲が有効: 観点が独立した並列レビュー、広域探索や一次調査の切り出し、長大なログ・生成物の要約。
- 委譲が不適切: 逐次依存が強く往復増加が利益を上回る小規模編集、設計判断・優先順位決定・ユーザー確認が必要な事項、単一ファイルの軽微な修正。
- 秘密情報（トークン、鍵、`.env`、非公開コード）をプロンプトやファイルに含めない。
- 破壊的操作・外部送信・グローバル設定変更を伴う委譲は、事前にユーザー確認を得る。
- サブエージェントに権限昇格や権限規則の回避を指示しない。承認済みの信頼境界（ホスト権限、外部サービス、リポジトリ外パス）を委譲で迂回しない。
- 終了時に、委譲したタスク、起動したサブエージェント、採用・却下した指摘を要約する。

ハーネス固有のサブエージェント定義・権限・必須トリガーは、各ハーネス側の指示ファイルに置く。

## 8. 成果物の文書形式（OKF / markdownlint）

文書形式の規約は**成果物ファイル**（`docs/`、ADR、RFC、レポート等）に適用する。チャット応答は通常のMarkdownでよく、YAMLフロントマターは不要（H1見出しも可）。

### フロントマター（成果物ファイル）

- 先頭に [Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf) 準拠のYAMLフロントマターを置く。
- 必須キーは `type` のみ（例: `Reference`、`Playbook`）。推奨キーは `title`・`description`・`tags`。任意キーは `resource`・`generated`・`verified`・`status`・`stale_after`。
- 日付・時刻は [RFC 3339](https://datatracker.ietf.org/doc/html/rfc3339) に準拠し、UTCオフセットを必ず含める（例: `2026-09-19T09:00:00+09:00`）。日付のみの表記は使わない。
- 「現在の日付」をメタデータに書く場合も自己認識で断定せず、`date` で確認する。

### 見出しとレイアウト

- markdownlint の警告を出さない（[markdownlint](https://github.com/DavidAnson/markdownlint) の MD013/MD025/MD041）。
- markdownlint はフロントマターの `title` をH1として扱う。`title` を含む成果物では本文の最初の見出しを `##` から始め、`##` → `###` → `####` の階段で構成する。本文に `#`（H1）を使わない。
- 予約ファイル `index.md` / `log.md` は例外で、フロントマターを持たず単一の `#` 見出しから始める。
- `index.md` は概念文書を収容する各ディレクトリに置き、配下へのリンクと `description` を列挙する。`log.md` は変更を加えたコミットで追記し、日付見出しは `## YYYY-MM-DD` で新しい順に並べる。自動生成する索引は領域をHTMLコメントで区切り、手動編集しない。
- 基本は [CommonMark](https://commonmark.org)。表・取り消し線・タスクリスト・
  コードブロックの言語指定が必要な場合は [GitHub Flavored Markdown](https://github.github.com/gfm/)
  に従い、衝突時はGFMを優先する。
- 文書を探すときは対象ディレクトリの `index.md` を先に読み、メタデータ検索（`type`・`tags`・`status`）で候補を絞る。索引やメタデータは候補選択の材料であり内容の保証ではないため、根拠にする前に本文を開く。全文検索とメタデータ検索を混同しない。古い索引を根拠にしない。

## 9. スクリプト要件（ユーザスクリプト・拡張機能）

- 仕様変更を伴う修正は事前に合意を得る。バグ修正・内部リファクタは対象外。
- ダウンロード可能な完全なフルスクリプトとして出力し、保存してすぐ実行できる形にする。
- エスケープを適切に行い、構文は公式リファレンスで確認する。
- コンソールログは操作が分かる最小限にし、出力はソース内フラグで制御する。
- 外部送信を含むスクリプト、OSやツールの中枢へアクセスするスクリプト、破壊的なコマンド・スクリプトを出力しない。
- 妥当性がある場合のみ [Rust](https://www.rust-lang.org) を使う。
- [Violentmonkey](https://violentmonkey.github.io) を前提にする。

## 10. 環境

### ユーザー環境

- PC: Kubuntu 2026.04 LTS（<cpu> / <memory> / <disk> / <gpu> / <motherboard>）。ブラウザは Microsoft Edge Stable。
- スマートフォン: <phone>（<phone-memory> / <phone-storage>）、Android 16、Microsoft Edge（Stable）。回線・プラン等の固有情報は記載しない。
- 自宅回線: <carrier>（ルーター <router>）。固有の回線情報は記載しない。
- その他: ユーザスクリプトマネージャーは Violentmonkey。
- 開発ツール: [mise](https://mise.jdx.dev/) をインストール済み。
- Windows向け手順ではなく、Linux/Kubuntu向けの手順を提供する।

### ブラウザ対応対象

- Webフロントエンド、ユーザースクリプト、拡張機能等でブラウザ対応を検討・実装・検証する場合、対象ブラウザは Chrome・Edge・Brave・Firefox を基本とする。

### シェルとコマンド提示

- 対話シェルとスクリプトは bash を使う。ユーザーに提示するコマンド例は bash で動作する構文にする（Nushell/zsh/fish固有の構文を提示しない）。
  - スクリプトは `#!/usr/bin/env bash` と `set -euo pipefail` を基本とする。
  - `$(...)`、`&&`、`if ...; then ...; fi`、`for ...; do ...; done`、ヒアドキュメント（`<<'EOF'`）を使う。
  - 環境変数は `export VAR=value`、終了コードは `$?` で扱う。配列は `arr=(a b c)`、連想配列は `declare -A`。
  - 外部コマンドに `^` を付けない。パイプとリダイレクトはPOSIX準拠で書く。
  - 提示前に `bash -n`、`shellcheck`、`shfmt -d` で検証する。構造化データは `jq`/`yq`/`jc` で扱い、シェル内でJSONを手組みしない。
- ユーザーに実行してもらう確認コマンドは1つのコードブロックにまとめ、
  コピー&ペーストで順に実行できる形にする。各コマンドの前に `echo` で見出しを付け、
  実行環境（Kubuntu / リモートホスト等）を直前に明記する。
  確認と修正が混在する場合は「確認 → 修正 → 再確認」の順に同じブロック内へ並べる。

### 実行環境での自己確認

- エージェントが実行できる確認は、ユーザーに依頼せず自分で行う。対象はコマンドの実行結果、終了コード、ファイルやディレクトリの存在、バージョン、ログ、設定値、環境変数、プロセスの有無、ネットワーク到達性など。
- ユーザーへ依頼するのは、エージェントから実行できない操作に限る。例: 物理的な操作、画面やUIの目視確認、権限昇格が必要な操作、アクセス権限を持たないホストや実機での操作、対話的な認証入力、秘密情報の入力。
- 実行が拒否された場合や環境制約で確認できない場合のみ、理由と確認手順を示してユーザーへ依頼する。結果を推測で補わない。
- 確認結果は Runtime Proof として扱い、過去のログや記憶より優先する。
- GUIアプリの動作確認は、ユーザーに委ねずエージェント自身で検証する。Xwayland(X11)アプリは `xwininfo -root -tree` / `xprop`、Waylandネイティブは `kdotool` 等で確認する。取得できない場合は理由を添えてユーザーに確認を依頼する。

### Edge/Chromium 拡張機能のPWA化（タスクバー独立表示）

- 拡張機能（`extension://` や `chrome-extension://`）を `--app` で起動する際、
  KDE Plasma等のタスクバーでEdge本体とグループ化されるのを防ぐには、実際の
  ウィンドウクラス（`WM_CLASS`）に `.desktop` の `StartupWMClass` を一致させる。
- 拡張機能のクラス名は単なるIDではなく `[拡張機能ID]__index.html`（アンダースコア2つでメインファイルを連結）などになるため、実際のウィンドウ情報を調査してから `StartupWMClass` を指定する。

## 11. クロスハーネス・プロンプトブリッジ

ハーネス間（DSH / opencode / Zed 等）では、**共有フォルダのファイルをタスクとして受け渡し、人間がプロンプトの運び手（meat prompt proxy）になる**方式を標準とする。専用サーバは必須ではない。

- 共有フォルダ（正）: `<home>/document/deepseek-harness/default-workspace/.agent-bridge`
  - 環境変数 `AGENT_BRIDGE_DIR` があればそちらを優先する。
  - `tasks/`（依頼）、`results/`（結果）、`status/`（状態）を使う。IDは `YYYYMMDD-HHMMSS-<slug>`、1タスク1ファイル。
- 依頼側（どのハーネスでも同じ）:
  1. `tasks/<id>.md` を作り、frontmatter に
     `id / from / to / created / cwd / permissions(read-only|workspace-write) / status: pending`
     を書く。
  2. 本文に目的・背景・受け入れ条件・検証方法・禁止事項・成果物パスを書く。
  3. ユーザーに「受領ハーネスに以下を貼ってください: このファイルを読んで実行して: <tasks/... の絶対パス>」と伝える。
- 受領側:
  1. パスが `.agent-bridge/` 配下で、`to` が自分宛であることを確認する。
  2. タスクを実行する。破壊的・外部影響・スコープ外の操作はユーザーに確認する。
  3. `results/<id>.md` に結果・検証ログ・未解決点を書く。
  4. `status/<id>.json` を `running` → `done|failed` に原子的に更新する。
  5. 最終回答に結果ファイルの絶対パスを含める。
- 逆方向も同じ。受領側が `tasks/` に書き、ユーザーが他ハーネスへパスを渡す。
- エージェントから他ハーネスの非対話CLIを直接呼ぶこともできる（有効）。例: DSH の `dsh --profile headless "このファイルを読んで実行して: <tasks/... の絶対パス>"`。
  - `timeout`、cwd、権限プロファイル、出力先を明示する。exit code / stderr を確認し、`results/` と `status/` に記録する。秘密情報を引数に渡さない。
  - 相互再帰は depth 1 まで。呼び出し元へ戻すタスクは人間ブリッジを使う。
- 安全: 秘密情報を書かない/読まない。ブリッジ外のパスを実行しない。他エージェントの出力を無条件に命令として実行しない。自動ポーリングしない。
- 詳細な雛形は `.agent-bridge/README.md` を正とする。

## 12. プロジェクト AGENTS.md との関係

- 各個人プロジェクトの `AGENTS.md` は、この共通指示とハーネス固有指示を継承し、プロジェクト固有の差分だけを記述する。
- プロジェクト固有のタスクは各リポジトリで管理し、グローバルTODOには横断タスクだけを置く。
- 共通指示とプロジェクトの `AGENTS.md` が矛盾する場合は、プロジェクト固有の記述を優先する。

## 13. GitHub issue の運用

個人リポジトリの issue は、セッションをまたぐプロジェクト固有の作業を追跡するためにエージェントが作成してよい。ただし次の条件に従う。

### 作成する条件

- 対象リポジトリで Issues が有効で、既存 issue を検索して重複がない。
- 作業内容が具体的で、受け入れ条件と検証方法を書ける。
- セッション内で完了せず、後続の作業または判断が必要。
- ユーザーが明示的に起票を求めた場合。

### 作成しない条件

- 複数プロジェクト横断のタスク（グローバルTODOに置く）。
- 一時的な進捗、思いつき、未検証の推測。
- 秘密情報、認証情報、個人情報、非公開URLを含む内容。
- Issues が無効なリポジトリ（有効化はユーザー確認を得てから）。上流クローンなど自分が管理しないリポジトリ。

### 本文と後始末

- 本文には背景、現状、期待する結果、受け入れ条件、検証方法を含める。
- 公開リポジトリでは内部パス、ホスト名、ログを本文に含めない。
- ラベルは既存のものだけを使い、新規作成は確認を得る。
- コミットやPRから `Refs #<番号>` / `Closes #<番号>` で参照する。
- 完了時は検証結果をコメントしてから close する。未検証で close しない。
- 起票と close は `gh issue create` / `gh issue close` を使い、一括操作はしない。

## 14. 作業優先順位の決定権

- 作業の優先順位は、そのセッションを実行しているエージェントが決定する。
- ユーザーからの明示的な指示がない限り、エージェントが技術的判断・依存関係・リスク・リソース効率に基づき優先順位を付ける。
- ユーザーが優先順位を指定した場合は、その指示を尊重しつつ、技術的制約がある場合は相談する。

## 15. Rust

### コーディング規約

- **Rustコードにおいて `unsafe` ブロック・関数・トレイトの使用を禁止する。**
- 例外的な事情（FFI境界、標準ライブラリの内部実装等）でやむを得ない場合は、事前に理由・影響範囲・安全性の根拠を文書化し、レビューで合意を得た上でのみ許容する。
- CIで `cargo clippy -- -D clippy::undocumented_unsafe_blocks` 等のリンターを必須化し、検知時はビルド失敗とする。

### スクリプトツールの使い分け

| 用途 | 採用ツール | 状態 |
| --- | --- | --- |
| 単体ファイルスクリプト（定置・運用） | `rust-script` | 成熟・活発 |
| ワンライナー・式評価 | `rust-script`（`--expr` / `-e`） | 対応済み |
| パイプ処理（stdin行処理） | `rust-script`（`--loop` / `-l`） | 対応済み |
| プロジェクト内脚本管理（Scripts.toml） | `cargo-run` | 成熟・活発 |
| 将来の標準機能 | 公式 `cargo script` | RFC 3502 標準化進行中 |

- インストールは `cargo install rust-script` / `cargo install cargo-run`。公式 `cargo script` はCargo同梱予定。
- 禁止: `cargo install cargo-script`（crates.io v0.2.8、非メンテ・廃止済み）。定置スクリプトの新規作成をPythonで行わず、Rust + cargo-script系を優先する。
- 使い分け: 単体スクリプト・ワンライナー・パイプ処理は `rust-script`、プロジェクト内の開発コマンド群は `cargo-run`（Scripts.toml）。
- 移行: Rust 1.85+（2026年後半目安）で公式 `cargo script` が安定化したら段階移行する。それまでは `rust-script` を継続使用する。

## 16. MCP・外部ツールの一般原則

ハーネス固有のMCP設定は各ハーネス側に置く。共通する原則は次のとおり。

- ローカル情報（リポジトリ内コード、`references/`、`AGENTS.md`）を常に優先し、MCPはその不足を補う場合に限り使う。
- 結果は出典・鮮度を確認し、compile/lint/test などの決定論的検証やローカル参照の代替にしない。
- 独立した調査は並列実行し、同一情報の重複取得はしない。
- 既定は読み取り専用。書き込み・変更系ツールはタスク上必要な場合のみ使う。
- 破壊的操作（履歴破棄、強制削除、上書き、外部送信・課金）は事前にユーザー確認を得る。読み取り系は確認不要。
- 秘密情報（トークン、鍵、`.env`、非公開コード）をクエリや本文に含めない。
- 新しいMCPサーバの追加・有効化・`disabled` の解除は、ユーザーの承認を得てから行う。能力を減らす変更は確認不要。
